# EvidenceGate 首位独立使用者招募与验证指南

目标不是找人点赞，而是验证一个没有参与开发的人，能否理解、运行并迁移 EvidenceGate。

## 优先找谁

按价值排序：

1. 正在做 OCR、票据、合同或文档 AI 的开发者；
2. 真实活动编辑、采购审核或财务复核人员；
3. 正在使用百炼、PaddleOCR 或视觉模型搭建工作流的同学；
4. 愿意提交 GitHub Issue 的技术写作者或开源新人。

暂时不要求对方贡献代码。能够独立运行并指出一个真实障碍，就已经有价值。

## 去哪里找

- FDE 共学营和阿里云百炼开发者群：寻找已经做过结构化提取或企业接入的人；
- 内容编辑团队或文化机构合作方：邀请一位活动编辑测试艺文案例；
- GitHub：在相关项目讨论区只回复真正相关的问题，不群发广告；
- 朋友或同事：优先找不熟悉本项目、但理解目标业务的人。

## 招募话术

> 我在做一个开源的文档 AI 证据门禁。它不替代 OCR，而是在模型输出进入 ERP、发布后台或数据库前，检查结构、证据和确定性规则，并把不确定结果交给人。想找一位没有参与开发的人做 30 分钟独立试用：从 GitHub 克隆、运行样例，再尝试描述一个你自己的业务字段。过程中可以随时放弃，我只记录耗时、失败和看不懂的地方，不收集真实敏感文件。你愿意帮我做一次吗？

## 30 分钟测试流程

### 0—5 分钟：交代边界

只告诉对方仓库地址和目标，不演示操作。确认不使用真实敏感文件。

### 5—15 分钟：独立首次运行

观察并记录：

- 是否找到 Quick Start；
- 是否理解 Node 版本要求；
- 是否成功运行 `npm test`；
- 是否理解三种路由；
- 第一次失败出现在哪里。

前 10 分钟不要主动指导。否则无法验证陌生人体验。

### 15—25 分钟：迁移到一个自己的场景

让对方只完成一项：描述一个候选字段、一个危险案例和期望路由。不要要求现场开发完整 Schema。

### 25—30 分钟：复盘

只问四个问题：

1. 你觉得它解决的是什么问题？
2. 哪一步最难理解？
3. 你会在哪个真实流程里使用它？
4. 什么条件满足后，你才愿意继续使用或推荐？

## 必须记录的证据

| 字段 | 记录内容 |
|---|---|
| 测试者背景 | 角色和相关经验，不记录不必要的个人信息 |
| 输入 | 使用的仓库版本、命令和合成样例 |
| 输出 | 路由、退出码和关键错误 |
| 耗时 | 首次运行、理解路由、描述新场景分别耗时 |
| 失败 | 环境、文档、概念或程序失败 |
| 人工修正 | 谁提示了什么，修正前后发生什么变化 |
| 最终判断 | 会使用、需改进或不适用，以及理由 |

## 首轮验收标准

- 3 位独立测试者中至少 2 位能在 10 分钟内完成 Quick Start；
- 3 位都能正确解释 `ACCEPT_CANDIDATE` 不等于业务批准；
- 至少获得 1 个此前未覆盖的真实领域案例；
- 所有失败和人工提示均记录，不删除不好看的结果；
- 不把 3 人测试宣传成市场验证或生产可用性。

## 把反馈带回 GitHub

优先让测试者自己开 Issue；如果对方不使用 GitHub，可以由维护者代录，但必须标注“maintainer-transcribed”，并让对方确认内容。一个清楚的失败 Issue 比十个礼貌性的 Star 更有价值。
